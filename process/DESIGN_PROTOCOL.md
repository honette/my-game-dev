# Design Protocol

すべてのゲームプロジェクトに共通する、人間とAIの共同設計の進め方。ゲームごとにコピーしない。

## 目的

このリポジトリの成果物は設計ドキュメントである。ゲームの実装は、ここで作った設計を外部の実装環境（Google Playground、Unity MCP 等）に渡して行う。

AIは単なる文章生成器ではなく、ゲームデザイナー・プログラマー・アーティスト・QAの視点を持つ共同設計者として扱う。

## AIとの開発方法

このリポジトリでは、AIに一度に全仕様を決定させるのではなく、**人間とAIが対話しながら段階的に設計を進める**。

### 基本フロー

1. 現在の設計文書をAIが確認する
2. 未決定事項や矛盾点をAIが提示する
3. 人間とAIが対話して仕様を決定する
4. 決定した内容を関連するMarkdownファイルへ反映する
5. 次の設計項目へ進む
6. 必要に応じて過去の仕様を見直し、関連文書も更新する

### AIによる勝手な仕様決定を禁止する

`TBD` や未定義の項目について、AIは重要なゲームデザインを勝手に決定してはならない。

AIは以下を行う。

* 選択肢を提示する
* メリット・デメリットを説明する
* 他の仕様との矛盾を指摘する
* 必要な仕様を質問する
* 仮案を提示する

最終的なゲームデザインの決定は人間が行う。

### 一度に進める範囲

原則として、1回の作業では1つの設計テーマに集中する。

例:

* プレイヤーの移動
* 攻撃システム
* Parryの仕様
* 敵の攻撃パターン
* ボス設計
* ステージ構造

複数のテーマにまたがる変更が必要な場合は、変更前にその影響範囲を説明する。

### 設計の確定

仕様が人間によって承認された場合、その内容をMarkdownファイルへ反映する。

会話の中だけで決定した仕様を正式な仕様として扱わない。

**Markdownファイルに記録されている内容を正式な仕様とする。**

### 設計の進行

設計は上流から下流へ進める。

概念 → システム → 具体的な数値 → 実装仕様

の順に詳細化する。

後から新しい発見があった場合は、既存仕様を変更してよい。
その場合は関連する設計文書との整合性を確認する。

### AIへの基本姿勢

AIは「答えを出す装置」ではなく、ゲーム設計を一緒に検討する共同作業者として扱う。

**質問 → 対話 → 決定 → 文書化 → 次の質問**

というサイクルを基本とする。

### 設計の判断基準

「それっぽい」仕様より、プレイヤーが実際に遊んだときの操作感・可読性を優先して記述する。

## 開発フェーズ

Phase 0〜6 はゲーム開発全体の道のりである。このリポジトリが担当するのは、各フェーズの実装に必要な設計を揃えること。実装側への引き渡しは、フェーズごとに `03_handoff/` の引き渡し書で行う（`DOC_CONVENTIONS.md` 参照）。

### Phase 0 — Design
ゲームビジョン、コアゲームプレイ、主要システム、キャラクター、ステージ、アート方針を定義する。

### Phase 1 — Core Prototype
ゲームの核となるシステムを最小構成で実装できるだけの仕様を揃える（例: アクションならプレイヤー1体、敵2〜3種類、基本の攻撃・防御・被弾・死亡・リスタート）。

### Phase 2 — Vertical Slice
短い1ステージ（とボス等の山場）を、最終品質に近い形で実装できるだけの仕様を揃える。

### Phase 3 — Content Production
ステージ、敵、ボス、装備、探索、NPC等の仕様を追加する。

### Phase 4 — Balance
難易度、配置、報酬、進行速度、チェックポイントの数値と調整方針を定める。

### Phase 5 — Polish
アニメーション、VFX、SE、UI、演出、チュートリアル、アクセシビリティの仕様を詰める。

### Phase 6 — QA
最初から最後までのプレイで確認すべき観点（進行不能、セーブ破損、Soft Lock、操作不能、重大な視認性問題等）を定める。

## 実装からのフィードバック

実装側で検証した結果（操作感、難易度、視認性の問題等）は、設計を見直す材料として扱う。
変更が決まったら、該当する設計文書と `PROGRESS.md` の Decision Log に反映する。

## 完了条件

「文書を書いた」ではなく、「実装側の AI が設計文書と引き渡し書だけを読んで、意図した体験を作り始められる」ことを完了とする。
