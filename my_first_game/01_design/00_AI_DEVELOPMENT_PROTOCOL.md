# AI Development Protocol

## 目的

AIを単なる文章生成器ではなく、ゲームデザイナー・プログラマー・アーティスト・QAの視点を持つ共同設計者として扱う。

このプロジェクトの成果物は設計ドキュメントである。ゲームの実装は、ここで作った設計を外部の実装環境（Google Playground、Unity MCP 等）に渡して行う。

## 基本原則

1. 一度にゲーム全体を設計しない。
2. 実装側に渡せる単位で小さく設計 → 文書化 → 整合性確認 → 次へ進む。
3. 仕様書にない重要な仕様を勝手に追加しない。
4. 既存仕様と矛盾する場合は、新しい仕様を書く前に既存仕様の更新を提案する。
5. 変更時は関連する設計文書も更新する。
6. アセットの仕様では既存アセットとの視覚的一貫性を優先する。
7. 「それっぽい」仕様より、プレイヤーが実際に遊んだときの操作感・可読性を優先して記述する。

## 開発フェーズ

Phase 0〜6 はゲーム開発全体の道のりである。このプロジェクトが担当するのは、各フェーズの実装に必要な設計を揃えること。

### Phase 0 — Design
ゲームビジョン、コアゲームプレイ、戦闘、プレイヤー、敵、ステージ、アート方針を定義する。

### Phase 1 — Combat Prototype
プレイヤー1体、敵2〜3種類、基本攻撃、防御、回避、被弾、死亡、リスタートを実装できるだけの仕様を揃える。

### Phase 2 — Vertical Slice
短い1ステージと1ボスを、最終品質に近い形で実装できるだけの仕様を揃える。

### Phase 3 — Content Production
ステージ、敵、ボス、装備、探索、NPC等の仕様を追加する。

### Phase 4 — Balance
難易度、敵配置、報酬、進行速度、チェックポイントの数値と調整方針を定める。

### Phase 5 — Polish
アニメーション、VFX、SE、UI、演出、チュートリアル、アクセシビリティの仕様を詰める。

### Phase 6 — QA
最初から最後までのプレイで確認すべき観点（進行不能、セーブ破損、Soft Lock、操作不能、重大な視認性問題等）を定める。

## AIへの作業ルール

各作業の開始時:

1. 関連する設計文書を読む。
2. 現在の進捗を確認する。
3. 今回の検討範囲を明示する。
4. 人間と対話して仕様を決める。
5. 決まった内容を設計文書に反映する。
6. 関連する文書との整合性を確認する。
7. 変更内容を進捗文書に記録する。

大規模な変更を一度に行わない。

## 実装からのフィードバック

実装側で検証した結果（操作感、難易度、視認性の問題等）は、設計を見直す材料として扱う。
変更が決まったら、該当する設計文書と進捗文書の Decision Log に反映する。

## 完了条件

「文書を書いた」ではなく、「実装側の AI がこの設計文書だけを読んで、意図した体験を作り始められる」ことを完了とする。
